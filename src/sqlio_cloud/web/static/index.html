Google Cloud SQL -- Setup Required
  1. Enable Public IP on your instance (GCP Console → SQL → Instance → Connections → Networking → Public IP → Enable).
  2. Add the Data Bench IP to Authorized networks (GCP Console → SQL → Instance → Connections → Networking → Authorized networks → Add a network). Enter the Data Bench IP shown above, or 0.0.0.0/0 for a throwaway test instance.
  3. Use the Public IP address as the hostname (e.g., 34.26.137.105). Do not use the connection name (project:region:instance) -- that is for the Cloud SQL Auth Proxy only.
  4. If SSL is required on your instance, Data Bench handles it automatically -- no client certificate is needed.
  5. You do not need to create the database ahead of time. If the database name you enter does not exist, Data Bench will create it automatically when you test the connection.
Azure SQL Database / Hyperscale -- Firewall Setup
  1. In the Azure Portal, go to your SQL Server (the logical server, not the database) → Security → Networking.
  2. Under Firewall rules, click + Add a firewall rule and enter the Data Bench IP shown above (or 0.0.0.0 - 255.255.255.255 for a throwaway test server).
  3. Optionally, check Allow Azure services and resources to access this server if Data Bench is running in Azure (e.g., Container Apps).
  4. Click Save -- firewall changes can take 1-2 minutes to propagate.
  5. You do not need to create the database ahead of time. If the database name you enter does not exist, Data Bench will create it automatically when you test the connection.
Azure SQL Managed Instance -- Setup Required
  1. Enable the public endpoint on your MI (Portal → MI → Security → Networking → Public endpoint → Enable). This can take 5-10 minutes to provision.
  2. Add an NSG inbound rule allowing TCP on port 3342 from the Data Bench IP shown above (or from 0.0.0.0/0 if this is a throwaway test instance).
  3. Use the public hostname -- it has .public. in it:
    yourmi.public.abc123.database.windows.net
    The default hostname from the portal (without .public.) is the private VNet endpoint and will not work.
  4. Port is 3342 (not 1433). This has been set automatically.
  5. You do not need to create the database ahead of time. If the database name you enter does not exist, Data Bench will create it automatically when you test the connection.

Smoke Test

          
~5-15 minutes

          
Quick sanity check with minimal load

          2K-row test table, 100 operations per I/O test, 2-point thread sweep. Runs: random reads, random writes, SHA-256 integrity verification, and 2 representative analytical queries (Q01 pricing summary, Q06 revenue forecast). Enough to validate connectivity, basic IOPS, latency floor, and query compilation. Execution time depends on network RTT and instance tier -- expect 5 min on premium instances, up to 15 min on Basic/Burstable tiers with high-latency links.
        

        

          
Standard

          
~20-60 minutes

          
Balanced coverage of all test types

          10K-row test table, 500 ops per I/O test, 3-point concurrency sweep. Runs every I/O test (random read, random write, sequential scan, mixed 70/30, bulk insert), SHA-256 integrity stress, concurrent transaction isolation (balance conservation), all 16 analytical queries at Scale Factor 0.01, and full network profiling (DNS, ping, connection setup, first-byte, bidirectional bandwidth). Produces a comprehensive baseline suitable for tier comparison, capacity planning, and SLA validation. Time variance reflects instance size: 20 min on General Purpose or higher, up to 60 min on low-DTU/Burstable tiers.
        

        

          
Full Stress

          
~60 minutes

          
Comprehensive with maximum concurrency

          50K-row test table, 2000 ops per I/O test, 6-point concurrency sweep (1 → 2 → 4 → 8 → 16 → 32 threads). Includes everything in Standard plus: isolation level anomaly testing (dirty reads, phantom reads, write skew under each isolation level), connection pool stress (burst concurrency 1 → 200), and analytical queries at SF 0.05 with 2 iterations for variance measurement. Designed for production-grade assessments, cloud tier selection, and regression testing. Expect ~60 min on mid-tier instances; may run longer on constrained tiers.
        

      


      
Tests Included
        Select which test categories to run. Each test exercises a different database subsystem: I/O tests measure storage-layer throughput and latency scaling; Stress tests verify ACID correctness and concurrency handling under load; Analytical tests benchmark the query optimizer and execution engine on complex joins and aggregations; Network tests isolate the transport layer from the database engine. Hover over individual test names below for detailed methodology descriptions.
      

      


      
I/O Block Size
        The size of the random binary payload (VARBINARY/BYTEA) stored in each row of the I/O test table. At 1KB-4KB, the workload is IOPS-bound: network RTT and index seek dominate, and throughput (MB/s) will be low even at high IOPS. At 8KB (the default, matching common database page sizes), you balance IOPS and bandwidth measurement. At 64KB+, the workload becomes throughput-bound: fewer ops/sec but higher MB/s, stressing buffer pool, TLS framing, and TCP window scaling. This size is also used as the page size for SHA-256 integrity verification.
